# 风栖 API

The backend uses Python standard libraries only. Start with python3 server.py --host 0.0.0.0 --port 18791. Configuration and hashed credentials are stored in TRIM_PKGETC; the ownership recovery journal and desired-fans.json are in TRIM_PKGVAR. Set FAN_DEMO=1 for simulated hardware; configuration and requested FAN modes may persist but hardware writes remain in memory. Demo status always includes demo: true.

FPK initialization uses server.py --init-auth-stdin to create only TRIM_PKGETC/auth.json, preserves existing credentials on upgrade, and never initializes the controller. Passwords must contain 10–128 characters, with spaces preserved. The FPK launcher requires this file before startup. Development/demo startup may use /api/setup.

All responses are JSON. Errors have {ok:false,error:"中文说明",code:"machine_code"}. GET /api/auth/status and static assets are public. All other data and hardware endpoints require the fan_studio_session cookie. Cookies use HttpOnly; SameSite=Strict, expire after eight hours, and are held only in server memory. Passwords use scrypt with an independent salt.

All POST requests require Content-Type: application/json and an Origin with exactly the request's Host. All authenticated POST requests also require X-CSRF-Token matching the current session's csrf_token. Non-IP hostnames must be localhost, the system hostname, or listed in FAN_ALLOWED_HOSTS (comma separated). There is no wildcard CORS policy. Login, setup and password changes are limited to eight attempts per minute per client address.

## Authentication

- GET /api/auth/status → {ok,setup_required,authenticated,demo,csrf_token?}
- POST /api/setup body {password} → {ok,csrf_token} and a session cookie. It succeeds once, when credentials do not exist.
- POST /api/login body {password} → {ok,csrf_token} and a session cookie.
- POST /api/password body {current_password,new_password} → {ok,csrf_token} and a rotated session cookie. Requires the authenticated session and CSRF token, verifies the current password, validates the new password at 10–128 characters, and revokes all older sessions. The current browser receives a fresh session.
- POST /api/logout → {ok} and an expired session cookie.

## Data

- GET /api/status → {ok,version,demo,time,system,channels,fans,rpm_inputs,fan_groups,alarms,mode_summary,driver_available,recovery_blocked,pending_recovery_ids,pwm_test,pwm_test_result}.
  - version comes from the packaged bin/version.txt; the build rejects a mismatch with manifest.version.
  - system.cpu_temp and system.disk_temp are the maximum readable values after applying the top-level exact-ID ignore list independently to CPU and disk sensors. system.raw_cpu_temp and system.raw_disk_temp retain the raw maxima for diagnostics and safety alerts; max_temp is computed from the effective CPU/disk values. High-temperature alarms continue to use raw readings, and identify an ignored peak when applicable.
  - channels are raw PWM output readings augmented with ownership, group ID, requested mode, effective mode, target duty, RPM fault and any write error. percent, pwm, and enable are current driver readings, not claimed fan RPM. An ignored channel includes `ignored:true`; its `percent`, `pwm`, and `enable` values are null and no permission or health check is performed.
  - fans and rpm_inputs are independently discovered hwmon tachometer readings.
  - recovery_blocked means the durable journal is corrupt and all new takeovers are paused. pending_recovery_ids identifies individual PWM outputs whose exact restore has failed; only groups containing those outputs are paused.
  - fan_groups are persisted FAN records, initially seeded one per stable RPM input identity, with manual additions supported. Each includes configured and manually verified PWM IDs, currently discovered outputs, optional RPM reading, ready, writable, owned, pending, testing, active mode, target and error. saved_mode/saved_percent report the durable requested settings; startup_error explains a failed restart restoration. source_temp reports this FAN's selected temperature. A group is ready only when every assigned PWM exists, is writable, and has been manually verified.
  - pwm_test is null or {id,started_at,remaining_seconds}; a separate backend timer owns the ten-second deadline even when normal poll_interval is 30 seconds. pwm_test_result is null or {id,ok,error,baseline_rpms,final_rpms,started_at,ended_at,reason}. RPM maps use raw RPM input IDs. The result never automatically approves wiring.
  - alarms are advisory. Displaying or ignoring an alarm never calls a control endpoint or changes PWM. High CPU/disk temperature alarms do not override the selected mode.
- GET /api/hardware → {devices,fans,pwm_channels,temperature_sensors,disks,demo}. disks lists physical block devices with per-disk temperature, stable `sensor_id` for SMART fallback readings, source (`hwmon` or `smartctl`), and availability status. SMART reads run asynchronously, are rate-limited, skip runtime-suspended devices and use smartctl's standby check. PWM outputs and tachometer inputs are separate hardware attributes. Their numbering does not identify a motherboard header or prove wiring.
- GET /api/config → {ok,config:{temperature_source,ignored_temperature_sensor_ids,ignored_pwm_ids,curve,poll_interval,fan_groups,legacy_pwm_candidates}}.
  - fan_groups: [{id,name,pwm_ids,verified_pwm_ids,rpm_id,rpm_verified,curve_mode,temperature_source,ignored_temperature_sensor_ids,curve}]. curve_mode is global or custom; global follows the top-level temperature_source/curve/exclusions, custom uses this FAN's saved temperature_source/curve/exclusions. Older records without these fields normalize to global and no exclusions. A PWM can belong to at most one group; marking a PWM verified is an explicit user attestation after manual testing. Newly discovered RPM inputs seed one FAN using that input as its confirmed reading; this does not assign or verify any PWM. Missing old hardware references remain visible as unavailable and cannot be controlled.
  - The top-level ignored_temperature_sensor_ids excludes exact sensor IDs by kind: CPU IDs only affect CPU overview aggregation and CPU traces; disk IDs only affect disk aggregation and disk traces. They also exclude those IDs from global curve selection, sensor-failure fallback and missing-node checks. GET /api/hardware and sensor detail views retain raw readings; high-temperature alerts remain based on raw readings and say when the peak node is excluded. A disk row can edit only that physical disk’s mapped temperature sensor IDs. Independent FAN curve exclusions remain scoped to that FAN’s custom curve.
  - ignored_pwm_ids makes each listed output skip value/mode/permission reads, health checks, tests and control. Ignoring a PWM detaches it from any FAN route. The API rejects newly ignoring any owned or tested output; unignoring permits reads again.
  - legacy_pwm_candidates are read-only historical references from older config formats. They do not reserve PWM outputs and are never treated as physical FAN detection or approved wiring.
  - curve: 2–12 points ordered by increasing temperature; temperature is 0–100°C and percent is a nondecreasing 35–100%. The final temperature and percent are user-defined; no endpoint is forced to 70°C/100%.
- GET /api/history?minutes=5|30 → {ok,minutes,available_span_seconds,items:[{time,cpu_temp,disk_temp,temperatures:{cpu:{sensor_id:value},disk:{sensor_id:value}},max_temp,fans:{id:rpm},channels:{id:percent}}]}; returns only the requested recent window and retains up to 2,400 samples in memory (about 40 minutes at one sample per second). available_span_seconds describes the full retained span so the UI can explain when both ranges contain the same short runtime history. temperatures preserves per-sensor readings so the overview can draw individually colored traces and omit ignored IDs. cpu_temp and disk_temp are the effective aggregates at sample time. Older samples without temperatures are not assigned to a specific sensor curve.
- GET /api/logs → {ok,items:[{time,level,message}]}; capped at 250 in-memory events. No passwords or session identifiers are logged.

## Control

- POST /api/control body {id,mode,percent?} where id is a FAN group ID. auto uses the selected global/custom curve, manual uses 25–100% (50% if omitted), full requests 100%, and monitor releases that group. A takeover requires every group PWM to be present, writable and manually verified; all outputs in the group receive the same target. Successful requests durably save the FAN mode and last manual percentage for restart.
- POST /api/release body {id?} releases one FAN group when id is present, or all non-ignored application-owned PWM outputs when omitted. Each PWM is restored to its own exact saved PWM and enable values.
- POST /api/release body {pwm_id} retries only that pending PWM output. It rejects actively controlled/tested outputs; use FAN release or test stop for those. This retry does not release unrelated FAN groups.
- POST /api/pwm-test body {id,action:"start"|"stop"} → current status. Start accepts a writable, unowned PWM without requiring a FAN assignment or manual verification; it records exact original state before requesting 100%. Only one test runs at a time. Start rejects pending recovery, corrupt recovery journal, or an output currently owned by a running FAN. Stop immediately uses the same exact restoration path as the timer. Tests are temporary and are never saved as a desired FAN mode.
- POST /api/config body containing supported config keys → {ok,config}. The entire updated configuration is validated and saved atomically. Active FAN names and curves can change; PWM/RPM routing cannot change while controlling or testing affected outputs. `ignored_pwm_ids` and `ignored_temperature_sensor_ids` are configuration keys; FAN groups may set independent curve sensor exclusions.

New FAN records monitor without PWM writes. Before a test or takeover, the application durably records each original per-output PWM and enable value. It verifies output writes; a failed group write triggers restoration of that group and retains failed recovery records. Explicit release also clears that FAN's saved requested mode. Graceful shutdown restores owned outputs while retaining desired FAN modes. Startup first recovers any previous ownership journal, then validates and resumes saved FAN modes individually; failed validation/write clears only the affected FAN's desired mode and attempts restoration. A failed restore remains pending and is never reported as monitoring restored to the motherboard. Independent FAN groups remain usable. A damaged recovery journal blocks all new takeovers and tests rather than guessing hardware values.

Temperature sensor failure or a confirmed RPM input that remains missing/zero after a six-second startup grace and two scan samples applies the configured 50% fallback to owned PWM outputs. High temperature thresholds only raise global alerts; automatic curve endpoints are user-defined within 0–100°C and 35–100%. PWM percentage is duty cycle, not actual motor RPM. Outputs without a confirmed RPM input cannot use stall detection.
